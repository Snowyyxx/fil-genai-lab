System design · LangGraph × MCP × Bedrock × ECS Fargate

An AI agent that calls tools over MCP, deployed to the cloud with zero keys in the container.

A FastAPI service wraps a LangGraph ReAct agent. The agent reasons with Amazon Bedrock and acts through an MCP tool server. It runs as a container on ECS Fargate and reaches Bedrock through an inherited task role — no credentials are ever baked into the image.

What it is

One agent, two planes

The whole project splits cleanly in two. A build plane (run once from a laptop) provisions cloud infrastructure and ships a Docker image. A serve plane (the running container) answers HTTP requests by looping an LLM against a tool. The single most important idea is that these two planes use different identities — which is what the colors below track.

Deployer identity — IAM user, static keys (build only) Runtime identity — task role, temporary creds (serve only) Data / control flow

How a message becomes an answer

Request flow (the ReAct loop)

When you type “What is 47*89 + sqrt(144)?” into the chat UI, this is what happens inside the running task:

Browser POSTs to /chat
Same-origin as the UI, so no CORS or mixed-content problem — the page is served by the same FastAPI app.
Agent asks the model what to do
The message + tool schemas go to Bedrock Nova via the Converse API. The model sees a calculate_expression tool is available.
Model emits a tool call
Instead of guessing arithmetic, it returns “call calculate_expression('47*89 + sqrt(144)')”. LangGraph routes this to the MCP server over stdio.
MCP tool computes and returns
The Python function evaluates it in a restricted namespace and returns 4195 back through MCP to the agent.
Model composes the final answer
The tool result is fed back to Bedrock, which writes the natural-language reply. The loop ends when there are no more tool calls.
FastAPI returns JSON
{ "answer": "...4195", "tool_invocations": 3 } — the UI renders the answer and a “🔧 tool calls” badge.
Why an agent and not one LLM call? The model is good at reasoning but bad at exact arithmetic. The ReAct loop lets it delegate the parts it's unreliable at to a deterministic tool — the essence of tool-using agents.
The core lesson · why two identities

The two-identity IAM model

Newcomers ask: “if roles are safer, why have an IAM user at all?” Because a role must be assumed by an already-authenticated principal — a role can't bootstrap itself. Something has to make the first call. That bootstrap is the user; everything after is roles.

◆ Deployer

IAM user + static keys · lives on your laptop (outside AWS)
  • Job: build the infra — push image, create ECS & roles.
  • Creds: long-lived access key + secret in .env.
  • Used by: deploy.py, once.
  • Risk: keys are permanent → must be gitignored & rotated.
  • Upgrade path: replace with SSO / GitHub OIDC (temp creds).

◆ Runtime

Task role · lives inside AWS (the running task)
  • Job: run the app — call bedrock:InvokeModel.
  • Creds: temporary, auto-rotated, injected by ECS.
  • Used by: the container, on every request.
  • Risk: low — if leaked, they expire on their own.
  • Keys in code: none. That's the whole point.
The rule: identities inside AWS (EC2, ECS, Lambda) get a role automatically — no user needed. Identities outside AWS (a laptop, external CI) need a pre-existing credential — a user, or SSO. Our task is inside → role. Our laptop is outside → user.
How it got to the cloud

Deploy pipeline

Every step is in deploy.py and is idempotent (create-or-reuse), so the whole thing re-runs safely.

Create the ECR repository
A private registry to hold the image. deploy.py ecr
Build & push the image
Docker build → get an ECR token via boto3 → docker login → push :latest.
Create the two IAM roles
Execution role (pull image + logs) and task role (bedrock:InvokeModel) — both trusting ecs-tasks.amazonaws.com.
Create the CloudWatch log group
/ecs/aws-mcp-agent — where container stdout/stderr lands.
Create the Fargate cluster
Needed the ECS service-linked role to exist first (created once per account).
Register the task definition
Fargate, 0.5 vCPU / 1 GB, image + both role ARNs + awslogs. Env has region & model only — no keys.
Run the service with a public IP
Default-VPC subnets + a security group open on 8000, assignPublicIp=ENABLED. No load balancer.
Resolve the public IP & verify
Poll the task → its ENI → public IP, then curl /health and /chat.

Why these choices

Design decisions

MCP over stdio, in-container

The agent launches the tool server as a subprocess and talks over stdin/stdout. One container, one process tree, no extra networking — the simplest thing that makes the MCP wiring real. (For many tool servers or independent scaling you'd switch to HTTP transport.)

Amazon Nova instead of Claude

Claude on Bedrock needs a one-time Anthropic “use-case details” form per account. Nova needs no form and supports tool-calling — so it unblocked the build immediately. The model id is a single env var, so swapping back to Claude later is one line.

Public IP, no load balancer

Cheapest and simplest for a learning deploy — the task gets a public IP directly. Trade-off: the IP changes on redeploy and there's no health-based routing. An ALB (≈$16/mo) buys a stable URL and rolling health checks when it's worth it.

Zero credentials in the image

The Dockerfile copies only code; .dockerignore excludes .env and key files. Locally we inject creds with --env-file; on Fargate the task role fills that gap. The image is safe to push to a registry.

Things that bit us (and the fix)

Gotchas

Bare Bedrock model id → ValidationException
Nova/Claude 4.x need the regional inference-profile prefix. Fix: use eu.amazon.nova-lite-v1:0, not amazon.nova-….
Claude → “use case details not submitted”
Anthropic models are gated behind a one-time console form. Fix: switched to Amazon Nova (no form).
ECR docker login failed — pass store empty
Docker Desktop's credential helper was uninitialized. Fix: a temp DOCKER_CONFIG (no credsStore) + explicit DOCKER_HOST.
CreateCluster → “service-linked role” error
First-ever ECS use in the account. Fix: create_service_linked_role(AWSServiceName="ecs.amazonaws.com"), then retry.
Secret pasted into requirements.txt
A base64 key broke pip install in the build. Fix: removed the line; gitignored all key files.
Operating it

Cost & teardown

The Fargate task runs 24/7 (~0.5 vCPU / 1 GB ≈ $15/mo) until stopped; ECR storage is pennies. Bedrock is billed per token on each /chat.

Two open risks while it's up: port 8000 is reachable by anyone (0.0.0.0/0) and each call spends Bedrock money; and the deployer keys were shared in chat — rotate them. Lock the security group to your IP, or tear down when done.
