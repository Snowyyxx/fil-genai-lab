01

The claim we’re decoding

A viral post described an open-source project — kimi-k3-in-c — like this:

the post “You can now run a 2.78 trillion parameter model on a CPU with 8.24 GB of RAM. A 176 KB pure C99 engine that streams the model’s experts from disk instead of loading them into memory. No GPU. No CUDA. No framework.”

Taken at face value this sounds impossible: a 2.78-trillion-parameter model would normally need terabytes of memory. The trick is that two facts combine so that the numbers stop fighting each other — one about the model, one about the operating system. This guide unpacks both, from zero, and lays out a path to build a working small version.

Essence: it’s a normal LLM engine whose feed-forward layers read their weights from a memory-mapped file on disk instead of RAM — and because the model only uses a few of its weights per word, only a few get read.

02

The one idea, then everything else is plumbing

Keep this picture in your head; the rest of the guide is just the details behind it.

see it run Prefer to watch it happen? Open the live simulator — a token flows in, the router picks its experts, and only those stream from disk into RAM, with the matching code line lighting up. Drag N and top-k and watch the numbers move.

Those are the two facts:

  1. The model is sparse (Mixture of Experts). Each layer holds hundreds of “experts,” but a tiny router uses only a handful per word. → §04
  2. The OS loads files lazily (memory-mapping). A memory-mapped file isn’t read until you touch it, and can be dropped from RAM when space is tight. Touch few experts → few bytes resident. → §05

To get there you first need to know what an LLM actually computes. That’s next.

03

Transformers, from zero

An LLM is a function that reads a sequence of words and predicts the next one. It does this by turning words into vectors of numbers and pushing them through a stack of identical layers. Here is the whole forward pass — the loop that runs once per generated word:

The pieces, defined once

TermWhat it is (plain)Why it’s here
TokenA word or word-piece; the model works in these units.Input/output are token ids.
EmbeddingA lookup table mapping each token id to a vector (e.g. 4096 numbers).Turns discrete words into math.
AttentionLets each word look at earlier words and pull in what’s relevant, via Query·Key·Value dot-products.How context is mixed in.
RoPERotary position encoding — rotates Q/K so the model knows word order.“cat sat” ≠ “sat cat”.

what to hold onto Two things dominate memory. FFN/expert weights are huge but sparsely used — the streaming target. The KV cache + attention are smaller but always resident — that’s your real RAM floor, the reason it’s “8 GB” and not “8 MB”.

04

Mixture of Experts — the sparsity that makes it possible

In a normal (“dense”) transformer, the FFN is one big pair of matrices that every word passes through. A Mixture-of-Experts layer replaces that with N separate FFNs (“experts”) plus a small router that picks the best top-k for each word. So the model can hold enormous total knowledge while each word only pays for k experts.

In pseudocode the MoE layer is tiny — and line 4 is where streaming happens:

def moe_layer(x, router_w):
    scores   = x @ router_w              # score every expert
    top, wts = top_k(scores, k=2)      # pick the best k + their weights
    out = 0
    for e, w in zip(top, wts):
        W1, W2 = read_expert(mmap, e)     # ← touches ONLY expert e on disk
        out += w * ffn(x, W1, W2)         # run it, scale by its weight
    return out

Some models also keep one or two shared experts that always run (a common backbone), plus the top-k routed ones. Doesn’t change the picture — still a small, fixed number of experts per word.

05

Memory & disk — how “streaming from disk” really works

Here’s the part people find magical, but it’s just how operating systems have worked for decades. When you memory-map a file (mmap in C, np.memmap in Python), the OS makes the file’s bytes appear at an address range in your program — but copies nothing into RAM. RAM fills in only when you actually read a byte.

Why file layout is the quiet hero

Paging is only cheap if an expert’s bytes sit contiguously on disk. Then “read expert 6” is one sequential run of a few pages. If an expert’s weights were scattered across the file, one lookup would fault in dozens of random pages — slow. So the offline exporter’s job is to lay each expert out as one contiguous blob. That layout choice is doing as much work as mmap itself.

the catch Disk is orders of magnitude slower than RAM, which is slower than a GPU’s memory. Streaming trades speed for capacity: you can run the model, but slowly (low tokens/second). And you still need hundreds of GB of disk to hold the full model — the “8 GB” is the RAM figure only.

06

Quantization — shrinking the weights

A raw parameter is a 32-bit float (4 bytes). At 2.78T params that’s ~11 TB — even on disk that’s a lot. Quantization stores each weight in far fewer bits (8, 4, even ~2) by keeping a small scale factor per group of weights and packing the rest as tiny integers.

# quantize a block: keep one scale, store ints
scale   = max(abs(block)) / 127
q_block = round(block / scale)         # now each weight is an int8

# dequantize on the fly when you read an expert
weight  = q_block * scale              # back to a float, at read time

Two things matter for this project: it makes the on-disk file small enough to be practical, and the dequant step happens as you stream — you read the packed bytes for the chosen expert and unpack them to floats just before the matrix multiply. Your dequant math must exactly mirror how the exporter packed them, or you get garbage.

07

The C you’ll need (the final phase)

We build in Python first, then port the hot path to C for the “176 KB, no framework” version. The C concepts that carry the project:

ConceptWhat it meansUsed for
PointersA variable holding a memory address; *p reads what it points at.Walking through weight bytes.
StructsA bundle of fields (like a record) describing, e.g., the file header.Model config, offsets, shapes.
malloc/freeManually ask for / return RAM. No garbage collector.Activations, the KV cache.
File I/O + fstatOpen a file, learn its size.Preparing to map the model.
mmapThe syscall that maps a file into your address space (the streaming core).Experts on disk → pointer.
Float/byte layoutHow numbers are laid out in memory; casting a byte pointer to float*.Reading weights, dequant.
SIMD / threads (later)Do many multiply-adds at once / across cores.Making the matmul fast.

The entire streaming mechanism in C is essentially this — the OS does the rest:

int fd = open("model.bin", O_RDONLY);
struct stat st; fstat(fd, &st);
/* map the whole file — copies NOTHING into RAM yet */
float *weights = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);

/* touch expert e → OS faults in just its pages */
float *W1 = weights + expert_offset(e);
/* ...use W1 in the matmul... */

That’s the whole trick in C: mmap once, index into it, and let demand paging stream the bytes. No read() loop, no manual cache.

08

What we’re building — two pieces & five phases

Every engine like this is really two programs:

  • An exporter (Python, run once): convert real model weights → your own binary format, quantized, with each expert laid out contiguously and a header of shapes/offsets.
  • A runtime (the small C engine): tokenizer → forward pass → sampling, where the MoE block reads experts from the memory-mapped file.

09

Reality checks (so the headline doesn’t bite you)

  • Speed. It’s disk-bound → low tokens/second. This is a “can it run at all” feat, not “run it fast.” A GPU or enough RAM to hold the working set is still far faster.
  • Disk, not RAM, is the real footprint. The full quantized model is still hundreds of GB on disk. The “8 GB” is only what’s resident at once.
  • You need the weights. We’ll prototype on a small open MoE (OLMoE, Qwen-MoE, Mixtral-scale) — not a 2.78T model you’d have to download in full.
  • Correctness is the grind. ~70% of the work is matching a reference model’s output exactly: one wrong transpose, RoPE detail, or dequant rounding and it outputs noise.
  • Claims from the wild. The specific project/numbers in that post are unverified here; the technique is decades-old and sound. Trust the mechanism, check the benchmarks.
connection to your own stack This is the same RAM-vs-capability tradeoff that OOM-killed qwen2.5:7b under Docker’s 3.5 GB cap and forced you to the 3B model — pushed to the extreme: run an enormous model on tiny RAM, but slowly.
