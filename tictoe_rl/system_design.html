1

What we are building, and the honest caveat

Three things share one board implementation: a training mode that plays hundreds of thousands of games against itself, an evaluation harness that grades the result against perfect play, and a play mode that serves the frozen policy over HTTP so a human can try to beat it.

Read this before writing a line

Tic-tac-toe has 5,478 reachable board positions — 765 once you collapse the eight rotations and reflections. That is small enough to store in a Python dict. Tabular Q-learning solves it exactly, and minimax solves it perfectly with zero training. As an engineering solution to the game, a deep Q-network is unambiguously overkill.

It is an excellent teaching vehicle for exactly that reason. Because a perfect oracle is cheap to compute, every claim the network makes can be checked against ground truth — not "the loss went down" but "the greedy policy matches an optimal move in 99.4% of all 5,478 states." That turns each DQN component into a measurable contribution instead of an article of faith. We build it as specified and lean hard on the oracle.

The pipeline is linear, and each stage hands the next a file on disk. That boundary is what lets the deployed container carry no PyTorch at all.

Framing the game as an MDP

Before any network exists, the game has to be pinned down as states, actions, and rewards. Two choices here quietly determine whether the rest works.

State: canonical, two-plane

The board is always encoded from the perspective of whoever is about to move. Plane 0 marks the mover's own pieces, plane 1 marks the opponent's. The network never learns "X" or "O" — it learns "me" and "them", which is why a single set of weights can play both seats and learn from every move of every game.

Two 9-bit planes rather than one 9-cell array of {-1, 0, +1}: it is a wash in expressive power, but the one-hot form removes any implied ordering between "opponent, empty, mine" and converges more cleanly on a small net.

ElementDefinitionShape / range
State sTwo binary planes over 9 cells, from the mover's viewplane 0 = my marks, plane 1 = their marks; a cell is 0 in both planes when emptyfloat32[18]

Reward r+1 my move completes a line · −1 the opponent's reply completes one · 0 draw or non-terminalassigned to the player who moved, not to the ply{−1, 0, +1}
TerminalThree in a line, or nine cells filledbool
EpisodeOne complete game5–9 plies
Discount γ0.95below 1.0 so a win in two moves is worth more than the same win in four — it breaks ties toward decisive playscalar

Reward attribution: per player, not per ply

The reward for winning lands on the player who made the last move, and the matching −1 lands on their opponent's previous move. So the loop buffers each player's pending transition and only commits it once the consequence is known — either the opponent has replied (giving a real s′) or the game has ended (giving a terminal reward). Writing transitions ply-by-ply as they happen mislabels the loser's final blunder as reward 0.

3

The sign flip that makes or breaks it

This is the single most important section in the document. Tic-tac-toe is a two-player zero-sum game, and the textbook single-agent Bellman target is wrong for it — not approximate, not suboptimal, actively counterproductive.

The reason is structural. You act in state s, and the state you land in, s′, has your opponent to move. The quantity max Q(s′, a′) is therefore the best outcome available to them. Adding it to your target teaches the network to steer toward positions its opponent loves.

terminal transition — nothing follows, so do not bootstrap
y = r

non-terminal transition — negamax
y = r − γ · maxa′ ∈ legal(s′) Qθ⁻(s′, a′)

The terminal case is not a footnote here. Games last five to nine plies, so a large fraction of every sampled batch is terminal; bootstrapping off a finished board injects noise into precisely the transitions that carry the only real reward signal in the whole problem.

Equivalent framing

You will also see this written as an "afterstate" or delayed-transition formulation, where the transition is stored only once the opponent has replied and s″ is used with a + sign. The two are algebraically the same. Negamax on a canonical board is chosen here because it keeps the replay buffer homogeneous and the sign convention visible in one line of code.

4

The network and the legality mask

The network is deliberately small: an 18→128→128→9 MLP with ReLU activations and a linear head, 20,105 parameters in total. It is sized to be trainable on a laptop CPU in minutes and small enough that its full weight set fits in a file you can read.

Illegal moves are handled by masking, never by penalty. Occupied cells are set to −∞ before any argmax, in both places it appears: choosing an action, and taking the max over next actions inside the target. Teaching legality with a −10 reward wastes capacity relearning a rule the board already knows, and it drags the value scale away from the meaningful ±1 range.

5

The self-play training loop

One network, one optimiser, one replay buffer. The environment alternates seats and hands back a canonical board each time, so the network is simply asked "here is a position from your point of view — what is each move worth?" without ever being told which colour it is playing.

train.py — inner looppseudocode
# One game. The env hands back canonical boards, so `s` is always "my view".
s, pending = env.reset(), {}          # pending[player] = (s, a) awaiting outcome
while not env.done:
    p  = env.to_move
    a  = eps_greedy(online, s, env.legal_mask(), eps)
    s2, r, done = env.step(a)         # s2 is canonical for the OTHER player

    # Commit this player's PREVIOUS move now that its consequence is known.
    if p in pending:
        ps, pa = pending[p]
        buffer.push(ps, pa, -r, s, False)   # opponent's r hurts us
    pending[p] = (s, a)

    if done:                          # terminal: flush BOTH seats, no bootstrap
        buffer.push(s, a, r, None, True)
        if opp(p) in pending:
            os_, oa = pending[opp(p)]
            buffer.push(os_, oa, -r, None, True)
    s = s2

# ---- one gradient step per environment step ----
S, A, R, S2, D = buffer.sample(256)
with torch.no_grad():
    q2 = target(S2).masked_fill(~legal(S2), -inf).max(1).values
    y  = R + (~D) * (-GAMMA * q2)     # NEGAMAX: minus, and zeroed when terminal
loss = huber(online(S).gather(1, A).squeeze(1), y)
loss.backward(); clip_grad_norm_(online.parameters(), 10); opt.step()

if step % 500 == 0:
    target.load_state_dict(online.state_dict())
Optional, and worth it

Dihedral augmentation. Every board has eight equivalent forms under rotation and reflection, and the Q-values transform with them. Pushing all eight into the replay buffer multiplies effective data roughly eightfold for a few lines of index arithmetic, and it removes the mild positional bias that otherwise shows up as the agent preferring one corner over its mirror image.

6

Grading against a perfect oracle

Loss curves in Q-learning are close to uninformative — the target is non-stationary, so the loss can drop while the policy gets worse. Because the game is small, we can do far better than proxy metrics: enumerate the state space and compare against a solved answer.

minimax.py is a memoised full-game solver, a few dozen lines, no learning involved. It exists only to grade, never to train, and it is not shipped in the container.

MetricMethodTargetReads as
Win rate vs random2,000 games, agent seated as X then as O> 92% as XBasic competence. Reached early and then stops moving — do not tune on it
Losses vs randomsame games0Any loss to a random opponent means blocking is unreliable
Draw rate vs minimaxPerfect opponent, both seats, ε = 0100%The headline number. Tic-tac-toe is a draw under perfect play, so a single loss is a real, locatable defect
Policy agreementAll 5,478 reachable states; is argmax Q in the minimax-optimal set?> 99%The strongest signal. Covers states self-play rarely visits, which is exactly where a DQN hides its gaps
Value calibrationMean |Q(s,a*) − minimax(s)| over the same states< 0.15Whether it knows a won position from a drawn one, or merely ranks moves correctly

The last two are the ones worth watching. Policy agreement is scored over every reachable state, not just the on-policy ones, so it catches the classic failure where an agent plays its favourite opening perfectly and falls apart in positions self-play under-sampled. When a run disagrees with the oracle, evaluate.py prints the offending boards — usually a small, related family, and usually diagnostic.

Expected shape of a healthy run

Win-rate against random saturates fast and is uninformative after that. Draw-rate against minimax is the metric that moves late: it typically sits well below 100% long after the random-opponent numbers look finished, then closes over the final third of training as ε anneals and the buffer fills with competent play rather than noise.

7

Serving: export, then three matmuls

Training is finished, weights are frozen, and there is nothing left for an autograd engine to do. export_weights.py pulls the six arrays out of the checkpoint and writes them to model/policy.npz; policy.py reloads them and runs the forward pass in NumPy.

policy.py — the entire inference engineno torch
import numpy as np

W = np.load("model/policy.npz")

def q_values(state18):
    h = np.maximum(0.0, state18 @ W["w1"] + W["b1"])   # ReLU
    h = np.maximum(0.0, h        @ W["w2"] + W["b2"])   # ReLU
    return             h        @ W["w3"] + W["b3"]    # linear head, shape (9,)

def choose(state18, legal):
    q = q_values(state18).copy()
    q[~legal] = -np.inf                            # mask, never punish
    return int(q.argmax()), q

That is the whole runtime. It is readable in one sitting, has no framework to version-pin, no CUDA probe on import, and a cold start measured in milliseconds — which matters on Fargate, where a slow import is a slow deployment.

The container

The image contains four Python files, a 82 KB weight file and one HTML page. It does not contain PyTorch, the training loop, the minimax solver or the checkpoints.

Why the runtime choice mattered

A plain pip install torch resolves to CUDA-enabled wheels and drags roughly two gigabytes of GPU libraries onto a Fargate task that has no GPU. It works, and it is slow and expensive in every dimension that matters — image pull time, ECR storage, cold start.

RuntimeApprox. imageNotes
skip torch, default index~2.5 GBShips CUDA libraries to a CPU-only task. Slow pulls, slow rollouts
skip torch, CPU index~370 MB--index-url https://download.pytorch.org/whl/cpu. Reasonable; still a framework for three matmuls
skip onnxruntime~250 MBPortable and standard, but adds an export format and toolchain for a 20k-parameter MLP
chosen NumPy only~170 MBBase image is most of it. Inference is readable in nine lines

Sizes are estimates for planning; confirm with docker images after the first build.

Deploying to ECS Fargate

Same shape as aws-mcp-agent: an idempotent deploy.py driven by boto3, callable one stage at a time, safe to re-run. One structural difference is worth calling out.

This app needs no AWS permissions at runtime

aws-mcp-agent needed a task role because the container calls Bedrock. Here the weights are baked into the image and the app talks to nothing — so the task role is empty or omitted entirely. Only the execution role is required, and that belongs to the ECS agent (pull from ECR, write logs), not to your code. Fewer permissions, less to reason about.

Cost — it runs until you stop it

A 0.25 vCPU / 0.5 GB Fargate task running continuously in eu-north-1 is roughly $9 per month, plus pennies for ECR storage and egress. Nothing scales it to zero on its own. python deploy.py down is the off switch and should be the last command of any demo.

Failure modes, in order of likelihood

Every item below has a symptom you can actually observe, so a stalled run can be diagnosed rather than guessed at.

  1. 1
    Sign error in the targetUsing +γ·max Q(s′,·) instead of −. Symptom: draw rate against minimax never rises above chance no matter how long it trains, while loss looks perfectly healthy. Check this first, always.
  2. 2
    Bootstrapping off terminal statesForgetting the (1 − done) factor. Symptom: values drift well outside ±1 and the agent misjudges won positions.
  3. 3
    Masking in only one placeMasking at action selection but not inside the target's max. Symptom: the agent is competent early but blunders in near-full boards, where illegal cells outnumber legal ones.
  4. 4
    Reward on the wrong plyWriting transitions as they happen instead of once the consequence is known. Symptom: the agent never learns to block — the losing move was recorded as reward 0.
  5. 5
    ε driven to zeroSelf-play with no exploration collapses to one deterministic game repeated forever. Symptom: replay buffer diversity dies, policy agreement stays low on unvisited states. Hold the floor at 0.05 in training; use ε = 0 only at serve time.
  6. 6
    Target sync mistunedToo frequent and it degenerates to vanilla Q-learning and oscillates; too rare and the bootstrap is stale for whole epochs. 500 steps is a starting point, not a law.
  7. 7
    CUDA wheels in the imagepip install torch without the CPU index. Symptom: a 2.5 GB image and multi-minute Fargate pulls. Avoided entirely here by shipping NumPy.
  8. 8
    Docker credsStore on this machineDesktop's pass store is uninitialised, so ECR login fails opaquely. Fix is the explicit DOCKER_HOST in step 3.
  9. 9
    Stale public IPNo load balancer means the address changes on every redeploy. Re-run deploy.py url rather than trusting a bookmark.
  10. 10
    The task left runningFargate bills by the second and nothing scales it to zero. deploy.py down.

Out of scope, deliberately

No terminal play mode — the browser UI covers interactive play, and evaluate.py covers automated checking. No prioritised replay, no duelling or double DQN: each is a worthwhile extension, but adding them before the baseline hits 100% draws against minimax makes it impossible to attribute what helped. No ALB and no HTTPS, which is fine for a demo IP and not fine for anything public.

Next step

Build order is engine.py → minimax.py → dqn.py → train.py, because the oracle is what tells you the trainer works. Confirm this design or flag changes, and coding starts there.
