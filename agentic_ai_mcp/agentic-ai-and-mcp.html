Field guide · Agentic systems & the Model Context Protocol

The agent is just a loop with tools and a stop condition.

Everything else — memory, planning, multi-agent, MCP, guardrails, evals — is engineering around that one fact. This is the working reference: what each piece does, when it earns its place, and what breaks in production.

01

What "agentic" actually means

An LLM becomes an agent when it decides its own control flow. That is the whole distinction, and it is a spectrum, not a category.

In a normal LLM call, you write the steps: retrieve, then summarise, then format. The model fills in blanks inside a path you fixed. In an agentic system, the model chooses what happens next — which tool to call, whether to call one at all, whether it's finished. You wrote the space of possible actions; the model wrote the sequence.

The useful framing is who owns control flow:

Control flow ownerNameYou getYou lose
You, entirelyPipeline / chainDeterminism, cheap testing, flat costCannot handle inputs you didn't anticipate
You, with model-chosen branchesWorkflowMost of the determinism, some flexibilityBranch explosion if you keep adding cases
The model, inside your guardrailsAgentHandles open-ended, unenumerable tasksVariable cost, variable latency, harder to test
The model, including its own toolsAutonomous agentGenuinely open-world capabilityReal safety surface; needs sandboxing

The default engineering instinct should be to sit as far up that table as the task allows. Agency is a cost you pay for flexibility you actually need. A classification task does not need an agent. A "look at this failing build, figure out why, fix it" task cannot be anything else, because you cannot enumerate the branches in advance.

The three properties that show up in every definition

  • Goal-directedness — it is given an objective, not an instruction. "Make the tests pass," not "run pytest."
  • Environment coupling — it can take actions that change the world and read the results back. Without tools, a model can only produce text about acting.
  • Iteration until a stop condition — it runs more than once, and something decides when to halt. That "something" is one of the most under-designed parts of most systems.
The honest test

If you can draw the full execution graph before running it, you built a workflow. If you can only draw the node types and the edges are decided at runtime, you built an agent. Both are legitimate. Only one needs the machinery in sections 10–13.

02

The loop

Every agent framework you will ever read the source of reduces to this. Understanding it in raw form means you can debug any of them, and can decide when you don't need one.

Written out, with no framework:

Four things in that snippet are where real systems fail, and they are worth naming individually.

Errors must be fed back, not raised

A tool that throws and kills the loop turns a recoverable mistake into a failed run. A tool that returns ERROR: unknown column 'usr_id'. Available: user_id, ... lets the model self-correct on the next turn. Tool error messages are prompts. Write them like prompts — say what was wrong and what to do about it.

Truncation is a policy decision

A tool returning 200 KB of JSON will blow the context window and cost more than the rest of the run combined. Truncate, summarise, or write it to a file and return the path. Returning a handle instead of a payload is one of the highest-leverage moves in agent design.

The step budget is a safety device

Without max_steps, a confused model will call the same tool forever and bill you for it. Budget in three currencies at once: steps, tokens, and wall-clock. Whichever runs out first should stop the run and say so honestly.

The stop condition is a design surface

"No tool calls" is the crude version. Real systems add: an explicit submit_answer tool the model must call to finish; a verifier that checks the result and can reject it; a human approval gate. Making finishing an explicit action rather than an absence of action makes the trace far easier to read.

ReAct, without the mystique

The pattern above is ReAct (Yao et al.) — interleaving reasoning traces with acting. When it was published, models needed to be prompted into "Thought: … Action: … Observation: …" text scaffolding. Modern models have tool calling trained in, and reasoning models produce the thinking natively. You almost never need to hand-build the ReAct text format any more; you need to understand it because every framework's internals are still shaped like it.

03

Anatomy: the six parts

Every agentic system, from a 40-line script to a platform, has these six layers. Naming them is how you diagnose a problem — nearly every bug belongs to exactly one.

  • Modelthe reasoner
    Chooses actions. Its tool-calling reliability, instruction adherence, and long-context behaviour set the ceiling for everything above it. Tier deliberately: a strong model for planning, a cheap fast one for extraction and classification inside tool implementations.
  • Contextthe working memory
    System prompt, task, history, retrieved documents, tool results. Finite, expensive, and degrades as it fills. Managing it is the discipline in §04 — the single highest-leverage area in practice.
  • Toolsthe hands
    The action space. Each is a name, a JSON Schema, a description the model reads, and an implementation. The description is prompt engineering; the schema is API design; the implementation is ordinary software with ordinary bugs.
  • Memorystate across turns
    Anything that survives beyond the current context window: conversation summaries, learned user facts, task scratchpads, vector stores. Distinct from context — memory is storage, context is what you loaded from it this turn.
  • Orchestrationthe control plane
    The loop itself: routing, retries, parallel branches, sub-agents, checkpoints, human approval gates, resumability. This is where LangGraph, the Agents SDKs, and hand-rolled state machines live.
  • Runtimewhere it actually runs
    Process model, sandboxing, secrets, concurrency, persistence, streaming to a UI, cancellation. The part demos skip and production cannot.
Diagnostic shortcut

Wrong tool chosen → context or tool descriptions. Right tool, wrong arguments → schema too loose, or missing examples. Right call, wrong result → implementation bug, not an AI problem. Loops forever → stop condition and budget. Forgets what it did → memory layer. Falls over under load → runtime.

04

Context engineering

Prompt engineering was about wording one message. Context engineering is about curating the whole set of tokens the model sees at each step — and it is where most agent quality comes from.

The loop re-sends everything every turn. So context has three properties that drive design: it is finite, it is paid for repeatedly, and its quality degrades as it grows. Models attend less reliably to material buried in the middle of a very long context, and irrelevant material actively distracts — more context is not more capability.

Budget the window explicitly

Write down, for your agent, roughly what each region costs. A worked example for a 200 K window:

RegionBudgetPolicy when it overflows
System prompt + tool schemas~5 KFixed. If it grows past this, you have too many tools (§05).
Task / user request~2 KNever trimmed.
Retrieved knowledge~20 KRe-rank, keep top-k, drop the rest.
Working history (turns + tool results)~120 KCompact oldest-first at ~80% full.
Headroom for the reply~30 KReserved. Hitting the wall mid-answer is a bug.

The four techniques

1 · Compaction

At a threshold, replace the oldest span of history with a model-written summary that explicitly preserves decisions made, facts learned, files touched, and open questions — and explicitly drops raw tool output. Test your compaction step; a bad summariser silently deletes the one detail the task depended on. Keep the most recent turns verbatim; recency matters most.

2 · Externalisation (write it down)

Give the agent a scratchpad — a file, a note tool, a structured plan object. Long-horizon work should persist state outside the window, so a compaction or restart doesn't lose the thread. "Write the plan to plan.md, update it as you go" is a startlingly effective instruction.

3 · Just-in-time retrieval

Don't pre-load everything the agent might need. Give it a search tool and let it pull what it needs when it needs it. This mirrors how a person works — you don't read the whole codebase, you grep. It trades a little latency for a very large context saving, and keeps what's in the window relevant.

4 · Sub-agent isolation

Spawn a sub-agent for a bounded piece of work; it burns its own window on exploration and returns a condensed result. The parent's context stays clean. This is the strongest argument for multi-agent designs (§07) — not "specialists collaborate," but context isolation.

Writing the system prompt

Aim for the smallest set of instructions that fully specifies the behaviour — but no smaller. Two failure modes bracket the right answer: brittle hard-coded if-else logic that shatters on the first unanticipated input, and vague "be helpful" prompts that assume shared context the model doesn't have.

  • Role and scope — what it is, what it must not attempt.
  • Tool policy — when to prefer which tool; what to do when a tool fails; when to ask instead of guess.
  • Stop criteria — what "done" looks like, in observable terms.
  • Output contract — exact shape of the final answer.
  • A few real examples — canonical, diverse, not an exhaustive rulebook.

Structure it with headings or tags (<tools>, <rules>, <output_format>). It parses better and, more importantly, it makes the prompt maintainable by a human six months later.

Cache-aware ordering

Prompt caching keys on a stable prefix. Put everything invariant first — system prompt, tool schemas, static policy — and everything that changes per turn last. A timestamp or a session id near the top silently invalidates the cache on every single call and can multiply your bill.

05

Tools: the real API design problem

A tool is four things, and people usually only take one of them seriously:

PartRead byDiscipline it belongs to
NameModelNaming — unambiguous, verb-first, no overlap
DescriptionModelPrompt engineering — when to use, when not to
Input schemaModel + validatorAPI design — constrain hard, enums over free strings
ImplementationNobody, until it breaksNormal software engineering

Rules that hold up

  • Design for the model, not for your database. Don't expose execute_sql and hope. Expose the three questions people actually ask. Every degree of freedom you hand the model is a degree of freedom it can get wrong.
  • Make wrong calls unrepresentable. Enums, patterns, ranges, required fields. A schema violation caught by the validator costs one cheap retry; a semantically wrong call that succeeds costs a wrong answer.
  • Return what helps the next decision. Not the raw API envelope — the fields that matter, plus a one-line summary if the payload is large. Consider returning a reference ("wrote 4,213 rows to /tmp/q1.csv") instead of the data.
  • Errors are instructions. "ERROR: date range exceeds 1 year. Narrow `since` and retry." beats a stack trace by a wide margin.
  • Flag the dangerous ones. Mark tools read-only vs destructive vs idempotent, and let the runtime — not the model — enforce approval on the destructive ones.
  • Keep the set small. Somewhere past a couple of dozen tools, selection accuracy drops and schemas eat the window. Fixes: namespace them, split across sub-agents, or add a discovery tool that surfaces only the relevant subset.
  • Parallelise the independent ones. Modern models emit several tool calls per turn. Executing them concurrently is usually free latency.
  • Idempotency keys on writes. Agents retry. Retries duplicate orders, emails, and payments unless the tool is idempotent.
The cheapest quality win

Read your own tool descriptions as if you were the model and knew nothing else about the system. Most "the model is dumb" bugs are a description that never said when to use the tool, or two tools whose descriptions overlap. Fixing wording is faster than fixing anything else in the stack.

06

Patterns worth knowing

These are the composable shapes. The first five are workflows — you own the control flow. The sixth is the agent. Most good production systems are workflows with one agentic node, not agents all the way down.

Prompt chaining

Fixed steps, each on the last one's output, with optional programmatic gates between. Use when the task decomposes cleanly. Trades latency for accuracy per step.

Routing

Classify first, then dispatch to a specialised prompt or a cheaper model. Lets you optimise each path separately instead of writing one prompt that hedges across all of them.

Parallelisation

Two flavours. Sectioning: split independent subtasks, run concurrently, merge. Voting: run the same task N times and take consensus — buys reliability on judgement calls.

Orchestrator–workers

Like parallelisation, except the subtasks are decided at runtime rather than predefined. The right shape when you can't know in advance how many pieces the work has.

Evaluator–optimiser

One model produces, another critiques against explicit criteria, loop until it passes or the budget runs out. Works when you can articulate what "better" means — translation, code against tests, writing to a rubric.

Autonomous agent

§02's loop, unbounded. Use when steps can't be predicted and you can verify results. Cost and latency scale with autonomy, so put a checkpoint at every irreversible action.

Two more you'll reach for

Plan-and-execute — produce an explicit plan first, then execute steps against it, re-planning when reality disagrees. Makes long runs legible and lets a human approve the plan before any work happens. The failure mode is a plan written before the agent knows enough to write it; always allow re-planning.

Reflection — after a failure, have the model write down why it failed and carry that note into the retry. Cheap, and it converts a repeated identical failure into a genuine second attempt.

Order of escalation

Single call → single call with tools → chain → route → orchestrator-workers → autonomous agent. Move one step down only when you've watched the current level fail on real inputs. Complexity added speculatively is complexity you will debug later.

07

Multi-agent, honestly

Multi-agent is oversold. The real justification is narrow but genuine: context isolation. A sub-agent can burn 100 K tokens exploring a dead end and hand back a 500-token answer. The parent never sees the mess. That is a real architectural win and it is mostly the only one.

When it genuinely helps

  • Wide parallel search — many independent lines of investigation, results condensed.
  • Hard boundaries — a sub-agent with strictly fewer tools and narrower permissions.
  • Adversarial review — a critic that never saw the author's reasoning gives an honest second opinion.
  • Genuinely different context needs — one agent needs the schema, another needs the style guide, neither needs both.

When it hurts

  • Shared mutable state. Agents editing the same files or rows in parallel produce conflicts no framework resolves for you. Serialise writes or isolate workspaces.
  • Decisions that need full context. If a sub-agent needs everything the parent knows to decide correctly, splitting just adds a lossy hop.
  • Cost. N agents means roughly N times the tokens, plus coordination overhead. Confirm a single agent actually failed first.
  • Debuggability. One trace is readable. Twelve interleaved traces are not, unless you built for it.

Two coordination shapes cover almost everything. Supervisor: one orchestrator owns the goal and delegates; workers report back and never talk to each other. Predictable, easy to trace, and the default. Handoff: control transfers between peers, each fully owning the conversation while it holds it — natural for staged flows like triage → specialist → billing, but you must define exactly what state travels with the handoff.

Write the contract down

The most common multi-agent bug is an underspecified sub-agent brief. The parent says "research the auth system"; the sub-agent returns three paragraphs of prose when the parent needed a list of file paths. Specify the task, the tools available, the budget, and the exact return shape — a schema, not a vibe.

08

Memory and retrieval

Context is what's in the window now. Memory is everything that outlives it. Four kinds, with different storage and different retrieval:

KindHoldsTypical storeLoaded
WorkingThis task's scratchpad, plan, intermediate resultsA file, or a field on the run stateEvery turn
EpisodicWhat happened in past sessionsSummaries in a DB, keyed by user/threadAt session start, or on demand
SemanticDurable facts — preferences, entities, domain knowledgeKey–value or vector storeRetrieved by relevance
ProceduralHow to do things — learned rules, correctionsVersioned files folded into the system promptAlways, or per-domain

The hard part isn't writing memory, it's invalidation. A stale preference is worse than no preference. Timestamp everything, prefer the most recent contradicting fact, let the user see and delete what's stored, and don't write a memory from a single ambiguous utterance.

RAG, in one paragraph

Chunk documents with overlap, embed, store, then at query time embed the query, retrieve top-k, and put the results in context. What actually moves quality, in rough order: chunking that respects document structure (headings, sections — not fixed character counts); hybrid search (BM25 keyword + vector, fused) because pure vector search misses exact identifiers and rare terms; a re-ranker over a wide first-pass retrieval; and metadata filtering so you search the right subset at all. Embedding-model choice matters less than any of these.

In an agentic system, prefer giving the model a search tool over stuffing retrieved chunks into the prompt. It can then query repeatedly, refine terms after seeing results, and stop when it has enough — which is exactly the behaviour you want, and it keeps the window clean (§04).

Always carry provenance

Every retrieved chunk should arrive with its source id and location. Without it the agent cannot cite, you cannot audit, and "where did that come from?" becomes unanswerable. Retrieval without provenance is a hallucination with extra steps.

09

MCP — the protocol layer

The Model Context Protocol is an open standard for connecting models to tools, data, and prompts. It turns an M×N integration problem into M+N.

Without it, every agent framework writes its own connector for every system: your LangGraph agent needs a Postgres tool, your IDE assistant needs a different Postgres tool, your internal chatbot needs a third. With MCP, you write one Postgres server and every MCP-speaking host can use it. The common analogy — "USB-C for AI applications" — is accurate about the intent: one connector shape, many devices on both sides.

Architecture

Host
The application the user interacts with. It runs the model, owns the agent loop, decides which servers to connect, and enforces permission. Examples: an IDE assistant, a desktop chat app, your own agent runtime.
Client
A connector inside the host, one per server, maintaining a single stateful session. The isolation is deliberate: server B cannot observe server A's traffic.
Server
A program exposing capabilities — tools, resources, prompts — over the protocol. Can be a local process or a remote service. Knows nothing about which model is being used.
Base protocol
JSON-RPC 2.0: requests with ids, matching responses, and one-way notifications. Stateful session, negotiated at connect time.

The primitives

Three flow server → client. The control model is the important column — it's what stops MCP from being "just tools with extra steps".

PrimitiveIsControlled byMethods
ToolsExecutable functions with side effectsThe model — it decides when to invoketools/list, tools/call
ResourcesReadable data identified by URI; no side effectsThe application — the host decides what to loadresources/list, resources/read, resources/subscribe
PromptsParameterised templates / workflowsThe user — typically surfaced as slash commandsprompts/list, prompts/get

Three flow the other way — client capabilities a server may call on:

CapabilityWhat the server asks forWhy it matters
Sampling"Run this completion for me"Servers get LLM capability without shipping their own model or holding your API key. The host stays in control and can require approval.
Roots"Which directories/URIs am I scoped to?"The client declares the boundary; the server stays inside it.
Elicitation"Ask the user for this field"Structured mid-operation input — confirmations, missing parameters — without the server inventing its own UI.

Transports

stdio — the host launches the server as a child process and speaks newline-delimited JSON over stdin/stdout. Zero network surface, trivially fast, ideal for local tools. This is where you should start.

Streamable HTTP — one HTTP endpoint; the client POSTs JSON-RPC messages and the server may reply with a single JSON response or upgrade to an SSE stream for multiple messages. Sessions are tracked by an Mcp-Session-Id header. This replaced the older two-endpoint HTTP+SSE transport, which remains only for backwards compatibility. Remote servers should use OAuth 2.1, treating the MCP server as an OAuth Resource Server that validates tokens issued for it specifically.

Lifecycle and wire format

Two error channels, don't confuse them

A protocol error (unknown method, malformed params) is a JSON-RPC error object — the model never sees it. A tool execution error (the query failed) is a normal result with isError: true and an explanatory text block — the model does see it and can recover. Returning execution failures as protocol errors is a common bug that makes agents unable to self-correct.

A server, end to end

The official Python SDK ships FastMCP, which derives the JSON Schema from your type hints and the tool description from the docstring — so the model-facing surface is the code itself.

A client, end to end

This is the piece that matters for building your own agent: connect, list, translate MCP tool definitions into whatever tool format your model API wants, then route calls back.

Wiring it into a host

Most hosts take a config block naming a command to launch. Same shape almost everywhere:

Use absolute paths — the host may launch from any working directory. Debug with the MCP Inspector (npx @modelcontextprotocol/inspector, or mcp dev server.py with the Python SDK), which gives you a UI to list and call everything without involving a model at all. Do that before you connect a model; it separates protocol bugs from prompting bugs.

stdio servers must never print to stdout

stdout is the protocol channel. A stray print() corrupts the JSON-RPC stream and the connection dies with an opaque parse error. Log to stderr, or to a file. This is the single most common first-time MCP bug.

Design rules for servers that hosts actually keep installed

  • Expose workflows, not endpoints. A 1:1 wrapper over 60 REST endpoints is a bad server. Three tools that answer the three real questions is a good one.
  • Tools vs resources. If it has side effects or needs computation, it's a tool. If it's static-ish readable context the host might want to attach, it's a resource. Read-only lookups that the model must decide to fetch are still tools.
  • Annotate honestly. The read-only / destructive / idempotent hints drive host approval UI. Lying about them breaks the user's trust model.
  • Version and evolve carefully. Renaming a tool breaks every prompt that referenced it. Add before you remove.
  • Fail with guidance. Same rule as §05 — the error text is read by a model that is trying to recover.
10

Guardrails and security

An agent is a program that takes untrusted input and decides which privileged actions to execute. Treat it that way.

Prompt injection is the defining threat

Any content the agent reads — a web page, an email, a code comment, a tool result, a Jira ticket — can contain instructions. The model has no reliable way to tell data from directive. Assume every retrieved token is adversarial.

What actually helps, in order of effectiveness:

  • Least privilege. The agent can only do what its tools allow. If it has no send_email tool, no injection can make it send email. This is the only defence that doesn't depend on the model behaving.
  • Approval gates on irreversible actions. Deletes, payments, external sends, production writes. Show the exact call and let a human confirm.
  • The lethal trifecta. Danger concentrates where three things meet: access to private data, exposure to untrusted content, and the ability to communicate externally. Break any one leg and exfiltration becomes much harder.
  • Mark untrusted regions. Wrap retrieved content in delimiters and state in the system prompt that content inside is data, never instructions. Helps; is not sufficient alone.
  • Validate outputs, not just inputs. Check the arguments of a tool call against policy before executing — a URL allowlist beats hoping the model didn't get talked into a webhook.

Layers to put around the loop

LayerRunsCatches
Input filterBefore the modelOff-topic, abusive, obvious injection attempts
Schema validationBetween call and executionMalformed or out-of-range arguments
Policy checkBetween call and executionAllowed action, wrong target — foreign account, prod DB, unlisted domain
Approval gateBefore irreversible actionsEverything else, by asking a human
Output filterBefore the user sees itLeaked secrets, PII, unsupported claims
Budget guardContinuouslyRunaway loops and cost spikes

MCP-specific hazards

  • Malicious servers. An MCP server you install is code you run with your permissions, and its tool descriptions go straight into your model's context. Audit before installing; prefer pinned versions.
  • Rug pulls. A server can change a tool's description after you approved it. Pin versions; re-review on change.
  • Confused deputy. A server holding a broad credential can be induced to act on behalf of a request it shouldn't honour. Scope credentials per-server, never share one token across servers.
  • Token passthrough. Don't accept a token issued for a different service and forward it. Validate that the token was issued for this server.
  • Cross-server composition. Server A reads untrusted data, server B can send it outward. Individually fine; together, exfiltration. Review the union of installed capabilities, not each in isolation.
Sandbox the runtime

If the agent runs code or shell commands, it belongs in a container with no host filesystem mount, an egress allowlist, no ambient cloud credentials, and a wall-clock kill. The model does not need to be malicious for this to matter — a confused agent with rm does the same damage as a hostile one.

11

Evaluation

Agents are stochastic and multi-step, so "it worked when I tried it" is not evidence. You need a fixed set of cases you can re-run on every prompt change, every model swap, every tool edit.

Three things to measure

LevelQuestionHow
OutcomeDid it get the right answer?Exact match, tests passing, a checkable assertion, or an LLM judge with a rubric
TrajectoryDid it get there sensibly?Compare the tool-call sequence: did it call the right tools, avoid needless ones, recover from errors?
CostWhat did it spend?Tokens, tool calls, steps, wall-clock — per case, tracked over time

Trajectory matters because outcome alone hides regressions: an agent that reaches the right answer after 14 flailing calls is a production incident waiting to happen, and an outcome-only suite scores it identically to a clean three-call run.

Building the suite

  • Start with 20 real cases, not 500 synthetic ones. Pull them from actual failures and actual user requests. Add every bug you fix as a permanent case.
  • Cover the shape of the space: happy path, ambiguous request, missing data, tool failure, out-of-scope request, adversarial input.
  • Run each case several times and record the pass rate. A flaky 60% is different from a solid 60%, and single runs will lie to you.
  • Prefer programmatic checks where you can get them — did the row get created, do the tests pass, is the JSON valid. They're free and they don't drift.
  • For subjective quality, use an LLM judge with an explicit rubric and require it to cite evidence. Then validate the judge against human labels on a sample; an uncalibrated judge is a confident random number generator.
  • Wire it into CI with a threshold. If the suite doesn't gate a merge, it will rot.
The fastest quality loop

Read traces. Sit down with twenty real runs and read them end to end. You will find more actionable problems in an hour of that than in a week of metric-staring — and every one of them becomes an eval case.

12

Observability, cost, and the runtime

You cannot debug what you cannot see, and an agent's behaviour lives in the sequence, not in any one call. Emit a span per LLM call and per tool call, nested under a run-level trace, carrying: the full prompt and response, the tool name and arguments, latency, token counts, cost, and the error if any. OpenTelemetry's GenAI semantic conventions give you a vendor-neutral shape; LangSmith, Langfuse, Braintrust and Phoenix all offer the UI on top.

Cost control

  • Tier your models. Strong model for planning and final synthesis; cheap fast model for classification, extraction, and routing. This is usually the single largest saving available.
  • Cache the prefix. Stable system prompt and tool schemas up front (§04). Large, repeated wins.
  • Return handles, not payloads. Every KB a tool returns is re-sent on every subsequent turn.
  • Hard budgets per run. Steps, tokens, and seconds. Stop and report honestly when one is hit.
  • Track cost per successful task, not per call — that's the number that tells you whether the system is viable.

Runtime concerns demos skip

  • Durability. Long runs must survive a process restart. Checkpoint state after each step; make the loop resumable from a run id.
  • Human-in-the-loop as a pause, not a block. An approval gate should suspend the run to storage and resume on the reply — not hold a thread open.
  • Streaming. Users tolerate a 40-second run if they can see the steps. Stream tool names and progress, not just final tokens.
  • Cancellation. A stop button must actually kill in-flight tool calls, not just hide the output.
  • Idempotency and retries. Retry transient failures with backoff; ensure write tools are safe to repeat.
  • Concurrency. Rate limits are per-account, not per-run. Centralise the limiter.

Frameworks are optional

Every framework above is a wrapper around §02's loop. Build one raw agent by hand before adopting one — you'll then choose based on what the abstraction buys you (checkpointing, streaming, retries) rather than on what it hides.

Part II

Depth

The first fourteen sections get a working agent. These eight are what separate one that survives contact with real traffic — where the token bill, the latency budget, the security review, and the 3 a.m. restart all start mattering at once.

15

Test-time compute: buying quality with tokens

You can spend more compute at inference to get better answers — but only if you have a way to select among the results. Without a selector, N samples is N× the cost and a random pick.

That rule is the whole section. Everything below is a different way of generating candidates and a different selector.

TechniqueGenerateSelectUse when
Extended thinkingOne answer, more reasoning tokens firstn/a — sequential refinementPlanning, math, multi-constraint decisions. Not retrieval or formatting.
Self-consistencyN samples at temperatureMajority vote on the answerAnswer space is small and comparable — a label, a number, a yes/no.
Best-of-NN independent attemptsA verifier scores themYou have a cheap, trustworthy verifier. This is the constraint.
Sequential revisionOne attempt, then critique-and-retryThe critic's pass/failErrors are localised and fixable — code against tests, drafts against a rubric.
Tree searchBranch at decision points, expand promising nodesValue estimate per nodeRarely worth it: needs cheap, dense intermediate signal. Most agent tasks only score at the end.

The verifier is the whole game

Ranked by how much you should trust them: programmatic checks (tests pass, code compiles, JSON validates, the invariant holds) > execution against ground truth > an LLM judge with a rubric > the same model grading itself, which is close to worthless because its errors correlate with its generation.

Practical consequence: when you can express success as a program, best-of-N is enormously effective. When you can't, prefer sequential revision with an explicit rubric, and cap it — quality plateaus after two or three rounds and then degrades as the model starts editing for the sake of editing.

Adaptive budgets

Spending maximum compute on every request is how you get a beautiful demo and an unviable unit economic. Route instead: classify difficulty cheaply, run the fast path, and escalate only on a signal — the verifier failed, the model expressed low confidence, the router flagged it, or the user rejected the first answer. Most traffic is easy; pay for the tail.

Thinking is not free, and not always helpful

Extended thinking costs output tokens at output prices and adds latency before the first visible byte. It reliably helps on planning and constraint satisfaction; it does roughly nothing for lookup, extraction, and formatting, and it can hurt on tasks where the right move is to just call a tool. Enable it per node, not globally.

Structured output and typed contracts

Anywhere an agent's output is consumed by code rather than a human, you need a contract. Three mechanisms, in ascending order of strength:

  1. Prompt and parse. "Reply with JSON." Works most of the time, which is the problem — the failures are rare enough to skip in testing and frequent enough to page you.
  2. Tool / function calling. The provider enforces the schema shape. This is the right default, and it's what you're already using for tools — a "return the answer" tool is just a tool.
  3. Constrained decoding. The sampler is masked at each step against a grammar compiled from your schema, so invalid tokens are literally unsamplable. Strongest guarantee available.
Syntax ≠ semantics

Constrained decoding guarantees the output parses. It does not guarantee the content is right — a model can emit perfectly schema-valid nonsense, and over-tight schemas can push it there. Validate values, not just shape, and keep a semantic check downstream.

One type, three uses

Define the shape once and let it serve as the model-facing schema, the runtime validator, and your code's static type. This is the pattern that removes an entire category of drift bugs.

Details that matter in practice

  • Put free-text reasoning fields before the fields they justify. Autoregressive generation means a reasoning field placed after category is a post-hoc rationalisation of a decision already made.
  • Always include an "I don't know" branch. A closed enum with no escape hatch forces a confident wrong answer on out-of-distribution input.
  • Discriminated unions for branching decisions. {action: "refund", amount: …} | {action: "escalate", reason: …} beats one flat object with a dozen optional fields the model must guess about.
  • Keep schemas shallow. Deeply nested objects with many optional fields measurably degrade both compliance and reasoning quality. Flatten, or split into two calls.
  • Stream partial JSON with an incremental parser when a UI is waiting — render fields as they close instead of blocking on the final brace.
  • On the MCP side, declare an outputSchema on a tool and return structuredContent alongside the human-readable text block. Clients that understand it get typed data; those that don't still get text.
17

Code as the tool interface

Direct tool calling has two costs that grow badly. Every tool's schema sits in context on every turn, so a large tool set eats the window before the task starts. And every intermediate result round-trips through the model — fetch 10,000 rows, the model sees 10,000 rows, filters them by generating text about them, then calls the next tool.

Code mode inverts this. Present the tools as a typed API inside a sandbox and let the model write a short program that calls them. Loops, filters, joins and aggregations happen in the sandbox at machine speed; only the final result enters the context window.

The arithmetic point is worth stating plainly: a sandbox does not make rounding errors, and a language model does. Any time a task involves aggregation, deduplication, sorting by a computed key, or set operations over more than a handful of items, moving it into code is a correctness improvement as well as a cost one.

Progressive disclosure

The companion idea: instead of loading every tool definition upfront, expose them as files the model can list and read on demand. It sees a directory of capabilities, reads only the two it needs, and the other ninety-eight cost nothing. Same principle drives skills — folders containing instructions plus executable scripts, loaded when a task matches, rather than a monolithic system prompt that carries every procedure the agent might ever need.

A cheaper middle ground when you don't want a sandbox: tool retrieval — embed your tool descriptions, retrieve the relevant subset per request, and pass only those to the model. Keeps a stable core set always loaded, and pulls the long tail in on demand.

The trade you are making

Code mode needs a real sandbox (§10) — you are executing model-written code. Errors move from "wrong tool argument" to "traceback", which is harder to constrain but, usefully, is also self-describing feedback. And an audit log of executed programs is far less legible than a log of tool calls. Keep genuinely destructive operations as explicit, approval-gated tools; let code handle the read-heavy work.

18

Durable execution

A long-running agent is a distributed system. It will be interrupted mid-run, and the interruption must not corrupt anything or lose work.

Three forces push you here at once: runs that take minutes to hours, approval gates that wait on a human who is asleep, and retries that must not re-charge a card. The answer is the same one workflow engines have used for years — persist state at every step boundary, and make replay safe.

What this buys you

  • Resume. A crashed process restarts from the last checkpoint instead of from zero. On a run that has already spent 200 K tokens, this is the difference between a blip and an incident.
  • Approval without blocking. Thousands of runs can sit paused in storage costing nothing. Surface them as an agent inbox — a queue of pending decisions with the exact effect described in human terms — and resume on the reply.
  • Time-travel debugging. Load any checkpoint, edit the state, and re-run forward from there. This is the single most useful debugging affordance in agent development, and you only get it if you persisted state as data.
  • Deterministic replay. If tool results are recorded, replay the whole trajectory without re-calling anything — reproducing a customer's exact failure locally, for free.
  • Event-driven agents. Once a run is a resumable record, a webhook, a cron tick, or an inbound email can wake it. The agent stops being a request/response call and becomes a process.

Rules for effects

Replay safety is entirely about side effects. Classify every tool: pure reads replay freely; idempotent writes replay safely given a stable key; non-idempotent effects — sending an email, charging a card, posting a message — must be recorded in an effect log before execution and skipped if the key is already present. Derive idempotency keys from run state, not from a timestamp or a random value, or replay generates a fresh key and duplicates the effect.

Build or buy

Framework checkpointers (LangGraph and similar) give you persistence and interrupt/resume with little work and are the right starting point. Dedicated durable-execution engines — Temporal, Restate, DBOS — give you stronger guarantees, retries, timers and exactly-once semantics, at the cost of a heavier programming model. Adopt one when the agent is orchestrating real business transactions rather than answering questions.

Latency and cost, in depth

Section 12 covered the basics. These are the levers that matter once you're actually serving traffic.

Where the time goes

An agent turn is: time-to-first-token (dominated by prompt length and cache state) + decode time (dominated by output length, including thinking tokens) + tool latency + serialisation. Measure them separately or you will optimise the wrong one. The usual surprise is that a "slow agent" is actually one slow tool called eleven times in sequence.

LeverTypical effectCatch
Prefix cachingLarge cut in input cost and TTFT on repeat turnsAny change to the prefix invalidates everything after it — order tokens stable-first (§04)
Parallel tool callsTurns N sequential tool latencies into oneOnly for independent calls; you must actually gather them, not await in a loop
Model cascadeMost traffic served by a cheap modelNeeds a reliable escalation signal, or you pay for both
Speculative prefetchHides tool latency behind model decodeRead-only tools only. Never speculate a write.

Perceived vs actual latency

A 45-second run that streams "searching orders… found 12… checking refund policy…" feels faster than a 20-second silent spinner. Stream the plan and the tool names, not just the final tokens. It is the cheapest latency work available and it also makes the agent legible, which builds the trust that lets users accept longer runs.

The number to track

Cost per successfully completed task, and p95 latency, not p50. Averages hide the runs that loop eleven times before succeeding, and those runs are simultaneously your worst cost outlier and your worst user experience. Alert on the tail.

Cache-hit rate is an observable

Providers report cache reads and writes per call. Put the ratio on a dashboard. A sudden drop almost always means someone added a timestamp, a session id, or a shuffled tool list near the top of the prompt — a one-line change with a very large invoice attached.

MCP at scale

Section 09 is enough to build a server. These are the parts you meet when servers become infrastructure.

Server → client requests

Sampling lets a server ask the host to run a completion. The server gets LLM capability without shipping a model or holding a key, and the host keeps control of cost, model choice, and approval:

Elicitation lets a server request structured input from the user mid-operation — a missing parameter, a confirmation — by sending a JSON schema the host renders as a form. It keeps servers from inventing their own UI and keeps the human in the loop at the point the decision is actually needed. Roots let the client declare the filesystem or URI boundaries the server should stay inside.

Composition: gateways and proxies

Past a handful of servers, hosts start hitting the tool-count ceiling from §05. The standard answer is a gateway server: one MCP server that is itself a client of many others, exposing a curated, namespaced union. It gives you a single place to do the things you'd otherwise do N times — auth, rate limiting, audit logging, tool filtering per user, and name collision handling (two servers both exposing search is a real and common problem).

The gateway is also where dynamic tool sets live: filter the exposed tools by the caller's scopes, then emit list_changed when they change. A read-only user simply never sees the destructive tools — which is a far stronger guarantee than a model instructed not to call them.

Auth and multi-tenancy for remote servers

  • Remote servers use OAuth 2.1, with the MCP server acting as an OAuth Resource Server that validates tokens and advertises its authorisation server via protected-resource metadata.
  • Validate the audience. A token must have been issued for this server. Accepting a token minted for another service and forwarding it is the token-passthrough vulnerability from §10.
  • Per-session credentials, not process env. A multi-tenant server that reads one DATABASE_URL from the environment serves every user as the same principal. Derive the identity from the session's token and scope every query by it.
  • Bind sessions. Session ids must be unguessable and tied to the authenticated user, or session hijacking is trivial.
  • Validate Origin on HTTP transports and bind local servers to 127.0.0.1, to block DNS-rebinding attacks from a browser tab.
Test servers like APIs, because they are

Contract tests over the protocol: list the tools, assert names and schemas haven't drifted, call each with golden inputs, assert on shape. That suite catches a renamed tool before it silently breaks every prompt downstream — and it runs in seconds with no model in the loop.

Capability security: designing for a compromised model

There is no known way to make a model reliably ignore instructions embedded in the data it reads. So stop trying to. Architect so that a fully compromised model still cannot cause harm.

This is the shift from detection (filters, classifiers, "ignore injected instructions" prompts — all useful, none sufficient) to containment: deterministic code outside the model decides what is permitted, and the model's output is a request, never an authorisation.

The dual-LLM pattern

Split the system by trust. A privileged model plans and calls tools but never sees untrusted content. A quarantined model reads the untrusted content but has no tools at all, and returns only structured data. The privileged model refers to that data through symbolic handles — $var_3 — and can pass it to tools without ever reading it. An injection in the source can therefore change a value, but it can never reach the component that chooses actions.

Taint tracking and capabilities

The stronger version: have the planner emit an explicit program describing the data flow, then run it through an interpreter that enforces policy on values. Every value carries provenance — where it came from, and who is allowed to see it. The interpreter refuses when a tainted value reaches a sink it isn't cleared for: content from a public web page cannot become the body of an email; a row from tenant A cannot be written to tenant B.

Capability tokens apply the same idea to authority. Rather than a tool that can act on any record, the agent holds a capability scoped to the specific records the current task legitimately touches. Even a perfectly-executed injection cannot widen its own scope, because the scope was decided before the untrusted content was ever read.

The practical checklist

  • secrets never in model-visible context — inject at the tool boundary
  • egress allowlist domains; block arbitrary URL fetch and webhook posts
  • scope per-tool credentials, least privilege, never one shared token
  • taint track provenance from untrusted sources to sinks
  • policy deterministic rules outside the model, not prompt instructions
  • approval show the human the effect, not the JSON payload
  • trifecta break one leg: private data · untrusted input · external comms
  • audit log every executed call with its arguments and its authoriser
Watch the approval fatigue curve

A gate that fires on every trivial action gets clicked through blindly within a day, at which point it provides zero protection while still annoying everyone. Gate on the small set of genuinely irreversible actions, describe the effect in plain language ("email 4,200 customers"), and make the safe path the default. A rarely-shown dialogue that people actually read beats a constant one they don't.

Improving the agent over time

Shipping is the start. The systems that get good are the ones with a loop from production traces back into the prompt, the tools, and eventually the weights.

The loop that always works

Read traces → find a failure class → add it as an eval case → change one thing → re-run the suite → ship if it improved and nothing regressed. Unglamorous, and it beats every clever technique below for the first several months of a system's life. The discipline that makes it work is that every fix becomes a permanent test.

Automated prompt optimisation

Once you have a metric and a labelled set, the prompt itself becomes a parameter you can search. Two approaches worth knowing: bootstrapped few-shot — mine your successful traces for exemplars and select the subset that maximises the metric, which is often a large win for near-zero effort; and reflective evolutionary search (the DSPy/GEPA family) — propose prompt mutations, score them, keep what wins, using an LLM's critique of failures to propose the next mutation. Both require a trustworthy metric first. With a noisy metric, you are just overfitting to your own judge.

Learning from trajectories

MethodNeedsGets you
Rejection-sampled fine-tuningA verifier + a strong teacher modelGenerate many trajectories, keep only verified-correct ones, SFT a small model on them. The cheapest real quality/cost win on a narrow task.
Preference tuning (DPO and kin)Paired better/worse trajectoriesSharpens style and format adherence; weaker for capability
RL on the environmentA real environment + programmatic rewardGenuine capability gains where reward is verifiable — code that must pass tests, tasks with a checkable end state. Expensive and easy to reward-hack.
Learned routersLogged difficulty vs outcomeA small classifier that picks the cheap or expensive path; often pays for itself immediately

The prerequisite for all of these is the same as for §15: a verifier you trust. If you can programmatically check success, every technique above opens up. If you can't, invest there first — it is the highest-leverage thing you can build, and it also gives you your eval suite for free.

Procedural memory, carefully

Agents can accumulate learned rules — "this customer's ids are prefixed differently", "never run the migration tool without a backup" — into a growing instructions file. It works, and it drifts: contradictory rules pile up, one-off corrections become permanent policy, and nobody notices the file is now 4,000 tokens of accreted folklore. Version it, review it like code, and re-run the eval suite whenever it changes.

Rollout discipline

Prompt and model changes are deploys. Shadow-run the new version against live traffic and diff the trajectories before switching; canary to a small share; keep the previous version one flag away. A model upgrade that improves your benchmark can still break the one tool call your whole product depends on.

Build order — the MCP application

The sequence for what we build next. Each step is independently verifiable, which is the whole point: when something breaks you know which layer owns it.

  1. One stdio server, one tool. Verify with the Inspector, no model involved. Confirms the protocol works before prompting enters the picture.
  2. Add a resource and a prompt. Feel the difference between model-controlled, app-controlled, and user-controlled — it's the mental model that makes the rest obvious.
  3. Write the client. Connect, list tools, translate schemas, run the §02 loop against them. This is the part that turns an MCP server into an agent.
  4. Register it with a host. Same server, different consumer, zero code changes. That's the M+N payoff, made concrete.
  5. Harden the tools. Tight schemas, guidance-shaped errors, truncation, annotations on the destructive ones.
  6. Add guardrails. Approval gate on writes, argument policy checks, step and token budgets.
  7. Add tracing. Span per LLM call and per tool call, with tokens and cost.
  8. Write the eval suite. Twenty real cases, outcome + trajectory, wired to a command you can run on every change.
  9. Serve it over Streamable HTTP with auth, if it needs to be remote.

And once that runs, the Part II moves, in the order they usually start paying off:

  1. Make the run durable (§18) — checkpoint per step, resume by run id, approval as an interrupt rather than a blocked thread. Everything else gets easier to debug once state is data.
  2. Add a verifier (§15, §22) — a programmatic check on the final result. It unlocks best-of-N, honest evals, and every learning technique at once.
  3. Type the boundaries (§16) — one Pydantic model per contract, reasoning fields first, escape hatches everywhere.
  4. Watch the cache-hit rate (§19) — stable prefix, parallel tool calls, cost per successful task on a dashboard.
  5. Contain, don't detect (§21) — taint boundaries and a deterministic policy check before any tool executes.
  6. Reach for code mode (§17) when tool schemas crowd the window or results get large enough that the model is doing arithmetic it shouldn't be.
  • stdio never write to stdout — log to stderr
  • paths absolute paths in host config
  • errors execution failures as isError, not JSON-RPC errors
  • schemas enums and patterns over free strings
  • budgets steps, tokens, and seconds — all three
  • cache stable prefix first, volatile last
  • approval gate every irreversible action
  • traces on before the first real user
