Playbook · FastAPI · LiteLLM · Bedrock · LangGraph · ECS Fargate

Laptop to public URL, one idempotent script.

The full path: containerise a FastAPI + LiteLLM stack, route to any Bedrock model, run a LangGraph supervisor that spawns subagents, push to ECR, and stand up Fargate with the right two IAM roles — plus a frontend on S3 you can update without rebuilding.

01

The shape

Four moving parts and two identities. Get those straight and everything else is mechanics.

Why LiteLLM sits in the middle

You could call Bedrock directly with boto3 or langchain-aws. Putting LiteLLM in front buys you four things that are painful to retrofit: one OpenAI-shaped protocol for every model, so swapping Nova for Claude for Llama is a config line rather than a code change; a single credential boundary, so only the gateway needs AWS access; routing, fallback and retries for free; and one place to attach logging, spend caps and tracing.

The cost is one more process. For a single-model toy it's overhead; the moment you have two models or two apps, it pays for itself.

Directory layout this playbook assumes

Mirrors your faraz_shayari project — app.py (FastAPI shell) · agent.py (LangGraph) · game.py (pure logic) · frontend.html · Dockerfile · .dockerignore · requirements.txt · docker-compose.yml · deploy.py · upload_html_to_s3.py.

02

Local first: docker compose

Never debug on Fargate what you can debug on your laptop. Compose gives you the exact topology you'll deploy — app container talking to gateway container over a private network — with a one-second edit loop.

depends_on without a condition is a lie

Plain depends_on: [litellm] waits for the container to start, not to be ready. LiteLLM takes several seconds to boot; your app will fire its first request into a refused connection and crash-loop. Always pair it with a healthcheck and condition: service_healthy.

LiteLLM → Bedrock: many models, one door

The config maps friendly names your code asks for to real Bedrock model IDs. Your application only ever knows the friendly name.

Calling it — it's just the OpenAI SDK

Bedrock model IDs that trip people up

FamilyID patternGotcha
Amazon Novaamazon.nova-{pro,lite,micro}-v1:0Needs a regional inference profile prefix in most regions: eu. / us. / apac.. The bare ID throws ValidationException.
Titan Embeddingsamazon.titan-embed-text-v2:0No profile prefix. Returns 1024-dim by default; you can request 512 or 256.
Anthropic Claudeanthropic.claude-*Requires submitting the use-case details form in the Bedrock console before access is granted. Nova needs no form — that's why it's the default here.
Meta Llama / Mistralmeta.llama* / mistral.*Availability varies sharply by region. Check before wiring up.
Inference profiles need permissions on both halves

A cross-region inference profile like eu.amazon.nova-pro-v1:0 fans your request out to the underlying foundation model in several EU regions. Your IAM policy must therefore allow both the profile ARN and the foundation-model/amazon.* ARNs. Granting only the profile produces an AccessDeniedException that names a region you never configured — a genuinely confusing error. See §07.

04

The FastAPI service

Keep app.py a thin HTTP shell. Business logic lives in modules you can import and test without spinning up a server.

Three decisions in there are worth copying deliberately:

  • lifespan, not module-level init. Building the graph at import time makes the module un-importable in tests and breaks reload. Compiling per-request is slow. The lifespan hook is the correct seam.
  • /health touches nothing external. ECS restarts the task when health fails. If health depends on Bedrock, a transient Bedrock error becomes a restart loop.
  • Serve the UI same-origin. The browser fetches / and posts to /move on the same host — no CORS preflight, no mixed-content block over plain HTTP.

LangGraph: a supervisor that spawns subagents

Tic-tac-toe is a good teaching target precisely because it's solved. You have a perfect verifier — minimax — so you can score the agent instead of admiring it.

The game, in pure Python

Write this first, and give the LLM none of it to guess at. Every line here is a thing a language model does worse than a for-loop.

The graph

Now the agentic part. Note where the LLM is and — more importantly — where it isn't.

What this demonstrates

PatternWhereWhy it's the right call here
Deterministic floorscout, tacticsLegality and two-in-a-row detection are exact in code and probabilistic in a model. Never spend a token on either.
Dynamic fan-outSend()N subagents where N is only known at runtime. Static parallel edges can't express that.
Context isolationanalystEach subagent evaluates one move with one board. It cannot be distracted by eight alternatives.
ReducerAnnotated[list, operator.add]The single most common LangGraph bug is parallel branches silently overwriting shared state. The reducer is what makes fan-in work.
Model tieringnova-lite / nova-proNine cheap narrow calls, one expensive synthesis call. Roughly the cost profile you want everywhere.
Evaluator–optimiserreferee → supervisorA verifier that cannot be argued with, feeding a bounded retry.
Now you can actually measure it

Because grade() exists, run 200 random reachable positions through the graph and report: % optimal, % suboptimal, % blunder, mean tokens, p95 latency. That's a real eval suite, in about thirty lines. Then change one thing — drop the analysts, or swap nova-pro for nova-lite in the supervisor — and see the number move. Most agent projects never get this, because most domains have no oracle. This one does, so use it.

Sample from mid-game positions, not from the empty board. Tic-tac-toe is a draw under perfect play from any opening, so grade() scores all nine first moves as optimal — correct, and completely uninformative. The signal lives at 3–6 pieces on the board, where blunders become possible. An eval suite drawn uniformly from all reachable states will look flatteringly good for exactly this reason.

Fan-out is a cost multiplier

Nine candidate moves means nine LLM calls per turn, per game. Fine for tic-tac-toe; a disaster if you naively port the pattern to a domain with hundreds of candidates. Prune with the deterministic layer first — pass only the top-k candidates to Send.

06

Containerising

Build for the platform Fargate runs

Fargate x86 tasks need linux/amd64. Building on Apple Silicon without --platform linux/amd64 produces an arm64 image that pulls fine and then dies with exec format error — a failure that gives you no useful clue. Always be explicit:

docker build --platform linux/amd64 -t myapp:latest .

(You're on x86 Linux, so this is a no-op for you today — but it costs nothing and saves an hour the first time you build from a Mac.)

Two sizing notes. Bake built artefacts, not build inputs — your faraz image ships embeddings.npy and skips the scraper and the raw corpus, which is exactly right. And if the image gets large, switch to a multi-stage build: compile wheels in a builder stage, then COPY --from=builder only the installed packages into a fresh slim base.

07

IAM: the two-identity model

This is where most people get stuck, and it's entirely because three different identities are involved and AWS names two of them almost identically.

IdentityWho uses itWhenNeeds
Deployer IAM userYou, from your laptopBuild timeECR, IAM, ECS, EC2 (VPC/SG), CloudWatch Logs, S3, STS
Execution role
ecsTaskExecutionRole		The ECS agent — not your codeBefore your container startsPull the image from ECR, create log streams
Task role
ecsTaskRole		Your application codeWhile runningWhatever your app calls — here, bedrock:InvokeModel

Execution vs task is the distinction that matters. If the image won't pull or logs never appear, it's the execution role. If your code gets AccessDeniedException from Bedrock at runtime, it's the task role. Both are assumed by the same principal — ecs-tasks.amazonaws.com — which is why the trust policy looks identical and people wire them backwards.

Two ARN shapes, and one of them has no account

Foundation-model ARNs carry an empty account field — arn:aws:bedrock:*::foundation-model/..., note the double colon — because the models are AWS-owned, not yours. Inference profiles are account-scoped and take your account id. Getting this wrong is the single most common cause of "I granted Bedrock and it still says AccessDenied".

The deployer user

For a lab account, attach the managed policies and move on: AmazonEC2ContainerRegistryFullAccess, AmazonECS_FullAccess, IAMFullAccess, CloudWatchLogsFullAccess, AmazonS3FullAccess, plus AmazonEC2FullAccess for VPC and security-group reads.

IAMFullAccess is the one to be deliberate about — it lets that key create any role. Keep the credentials out of git (they're in your .dockerignore already), rotate them periodically, and if this ever becomes shared infrastructure, replace the user with a role you assume via SSO.

Where credentials come from, in order

boto3 resolves: explicit kwargs → environment variables → ~/.aws/credentials → container credential endpoint → EC2 instance metadata. That fourth one is the magic: on Fargate the ECS agent injects AWS_CONTAINER_CREDENTIALS_RELATIVE_URI, boto3 finds it automatically, and the task role's temporary credentials appear with no code change. This is why the identical image runs locally with --env-file .env and on Fargate with no keys at all.

08

ECR: build, tag, push

Tag with the git sha as well as latest. latest is what the task definition points at for convenience; the sha is what lets you roll back to a specific build when latest turns out to be broken. Without it, "roll back" means "rebuild from an older commit and hope".

09

Fargate: cluster, task, service

Four objects, in this order. Each depends on the one before it — which is exactly why the deploy script is staged.

  • 01log groupCreate /ecs/<app> before the first task runs. The awslogs driver does not create it for you by default, and a task whose log driver fails to initialise dies instantly with nothing written anywhere.
  • 02clusterA namespace, essentially. Free. capacityProviders=["FARGATE"].
  • 03task definitionThe immutable blueprint: image, cpu/memory, ports, env, log config, and both role ARNs. Every register creates a new numbered revision.
  • 04serviceKeeps N tasks alive, replaces unhealthy ones, and handles rolling deploys.
CPUValid memoryFits
256 (.25 vCPU)512 / 1024 / 2048Tiny API. Too small for LiteLLM + app together.
512 (.5 vCPU)1024 – 4096 (1 GB steps)Sensible default for one FastAPI service.
1024 (1 vCPU)2048 – 8192App + sidecar gateway, or heavier numpy work.
2048 (2 vCPU)4096 – 16384Rarely needed if the model runs in Bedrock, not in your container.

Invalid pairs are rejected at registration — that's the good case. The bad case is under-provisioning memory: the container gets OOM-killed mid-request and the service quietly restarts it, which reads as random 502s.

Networking

The public IP changes on every deploy

Fargate assigns a fresh ENI, and therefore a fresh public IP, each time a task is replaced. Fine for a demo you're sharing today; useless for anything anyone bookmarks. When you need stability, put an Application Load Balancer in front — you get a stable DNS name, health-check-driven rolling deploys with no downtime, and HTTPS via ACM. The task then moves to a private subnet with the security group locked to the ALB. Budget roughly $16–20/month for the ALB itself.

Frontend on S3

Two genuinely different approaches, and it's worth being deliberate about which you're using.

A · App fetches from S3B · Browser loads from S3
Browser hitsYour Fargate URLThe S3 URL directly
API calls areSame-originCross-origin
CORS neededNoYes — and HTTPS→HTTP is blocked as mixed content
Update UI byRe-uploading to S3, restarting the taskRe-uploading to S3
Good forOne app, one URL — your current setupA real SPA, fronted by CloudFront

Option A is what faraz_shayari does and it's the right call for a single service: the app fetches the HTML from S3 once at first request, caches it in memory, and serves it from /. You update the UI by replacing the object in the bucket — no image rebuild, no ECR push. Just restart the task to clear the cache.

If you go with option B — static website hosting

Then you must handle CORS and mixed content

A page served from HTTPS (S3 or CloudFront) cannot call http://<fargate-ip>:8000 — browsers block mixed content outright, and no CORS header fixes it. Option B therefore forces you to put HTTPS in front of the API too: an ALB with an ACM certificate, or CloudFront with the API as a second origin. This is precisely why option A is the right default until you actually need a separate frontend.

11

deploy.py: the staged driver

Everything above, in one re-runnable script. Two properties make it worth the effort: idempotent, so re-running is always safe, and staged, so you can re-run just the part that broke.

Why boto3 and not CloudFormation / CDK / Terraform

For a lab you own end to end, a 200-line boto3 script is faster to write, trivially debuggable, and teaches you what the API actually does. The trade you're making is real: no drift detection, no dependency graph, no destroy. Once this becomes shared infrastructure with more than one person deploying it, move to Terraform or CDK — the script's job is to make you fluent enough to know what those tools are generating.

Operating it

--desired-count 0 is the most useful line in that block. It stops all compute charges while leaving your cluster, task definition, roles and image exactly as they are. Set it back to 1 and you're live again in about a minute. Use it every time you stop working for the day.

The thing that actually bills you

Not the deploy — the task you left running. A forgotten Fargate service is a quiet ~$18/month. Set a Budget alert at $10 in Billing, and get in the habit of --desired-count 0 when you walk away.

Deploy-day checklist

  • .env in .dockerignore and .gitignore
  • platform built for linux/amd64
  • bind uvicorn on 0.0.0.0, not localhost
  • health /health calls nothing external
  • logs log group created before first run
  • roles exec = pull+logs, task = bedrock
  • arns foundation-model has an empty account field
  • publicip ENABLED, or ECR is unreachable
  • tags pushed the git sha as well as latest
  • retention set on the log group
  • budget alert configured at $10
